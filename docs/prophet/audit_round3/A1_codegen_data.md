# A1 Code generation and data manipulation (audit round 3)

Audit date: 2026-11-22. Read-only audit. Labels: **measured-live** (a live mission snapshot in `data/`), **measured-repro** (a small read-only Python run against the current code), **inferred** (read from code, not run).

## Summary

1. The planner's sandbox code produces silent wrong data more often than it crashes. Of 85 sandbox cells in the six live runs, 23 failed (27%), but the most damaging errors passed without any failure: a calendar folded into the wrong days, dates shifted by position, and hard-coded cleaning dates.
2. The worst single case is retail rep4. A business-day rebuild (`build_series(freq='B')`, `dropna`, positional `bdate_range`) moved the saved series to end on 2011-11-04 while the raw file runs to 2011-12-08. The "next 14 trading days" forecast (2011-11-07 to 2011-11-24, £1.14m) therefore covers dates already observed, and the answer states it.
3. Helpers default to convenient but wrong behaviour: `prepare_series` interpolates closed days (about 2.9m, 15% of sales, invented in the retail file, measured-repro), `build_series(freq='B')` folds weekend sales into Friday with no report, and the TimesFM zero floor switches off when a single returns day is negative (measured-live: negative Saturday forecasts of -3,125 and -3,606).
4. The gates do not catch these. The ledger accepts typed numbers that contradict the raw file (rep4 negative dates are wrong), `check_forecast` has no date-continuity test, and the non-negative check is exempt exactly when the history has a negative.
5. Two claims in the audit brief do not hold. The Beijing "2 of 12 stations left out" is a planner misread of the envelope (the file holds all 12), but the final answer repeats it as fact. The rep3 cleaned series lost no weekly cycle (period 7, strength 0.64); the lost cycle is rep4 only (measured-live).

## Checked and found sound

- `_resolve_input` (prophet_lib.py:212-226) handles the `in/carried/out/...` slip. Electricity obs 10 showed a useful FileNotFoundError listing the files that exist.
- `panel_backtest` AttributeError text (electricity obs 20) teaches the fix. Use it as the template for A1-10.
- The `save_series` NaN refusal (prophet_lib.py:994) is right to refuse, but its wording ("fill or drop them") invited the dropna path in rep4. Fold into A1-01 and A1-03.
- TimesFM floors correctly when the history is non-negative (timesfm.py:76-80). The gap is the domain choice, not the arithmetic (A1-04).
- `prepare_series` does report duplicate dates and the cut-off leading and trailing periods (prophet_lib.py:1172-1245). The defect is the default sum (A1-11).
- The rep4 answer's description of the 80% total range (between the independent and together bounds) follows the tool's own wording and is not the planner's invention.

## What good looks like

A principal analyst's code would differ in five ways.

1. **Calendar first, as a fact.** One cell prints, per weekday, the share of periods with a record and the first and last dates, then writes the calendar down: "Saturday closed, Sunday trades". It never re-dates values by position and never assumes Monday to Friday. Dates stay as keys until the forecast step.
2. **Every transform states what it changed, by row.** Each step prints rows before and after, the changed dates with old and new values, and the sum before and after. A changed-row list that matches the flagged-row list is the check, not a count.
3. **Rules find rows; the analyst decides per rule.** Negatives and spikes are flagged by a rule, the rows are printed, and each row is kept, removed or replaced by its own reason. No date is typed from memory.
4. **The model's domain is declared.** Sales, counts and prices are non-negative by definition, so the forecast is floored and the number of floored steps is reported. A genuinely signed series is labelled as such.
5. **Claims come from the same frame as the figure.** The ledger quotes printed RESULT lines, the answer quotes those figures, and file shapes are read through the helpers (`load_forecast`, `load_ledger`, `findings_by_id`) after one `len()` and `keys()` print. After two failures of one kind, the analyst reads the object's type rather than resending the cell.

## Limitations

- The DST finding (A1-11) is a repro, not a live result; all six live runs used daily data.
- Rep3 and rep4 differ in method, so the live counts are not a controlled comparison. The failure-rate-by-length figures are directional with small n.
- "Not measured" means I did not find a live result changed by that defect, not that none occurred. For A1-07 the mechanism is verified and the live effect is not.
- No external best-practice references were fetched; every claim above rests on code, live snapshots or local repro runs.
